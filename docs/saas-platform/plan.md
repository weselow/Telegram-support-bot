# Сервис онлайн-чата для сторонних сайтов — план

**Дата:** 2026-08-04
**Статус:** обсуждение, план чернового уровня
**Эпик в трекере:** см. `bd list --label saas`

## Цель

Превратить бота поддержки, работающего сейчас на один бизнес, в сервис, которым
пользуются разные владельцы сайтов. У каждого — свой сайт с виджетом, свой бот в
Telegram и своя группа поддержки. Управление — через админку.

Что должно быть в админке:

- **Сайт.** Владелец добавляет адрес сайта и получает короткую строку для вставки.
  Тут же настройки внешнего вида: аватар и имя оператора, оформление кнопки вызова чата.
- **Бот.** Владелец заводит бота у @BotFather и вписывает его токен.
- **Группа.** Владелец создаёт группу в Telegram, добавляет туда своего бота и
  отправляет код из админки. Смысл — избавить его от поиска внутреннего номера группы.
- **История обращений** (желательно, но можно позже).

## Находки: как устроено сейчас

Обследование кода 2026-08-04. Всё приложение построено под одного владельца —
это не настройка, а несущая конструкция.

| Что | Где | Почему мешает |
|---|---|---|
| Один экземпляр бота на процесс | `src/bot/bot.ts:14` | Токен берётся из переменной окружения, работает опросом Telegram. Сервисы и фоновые задачи импортируют этого бота напрямую (`services/web-chat.service.ts`, `jobs/sla.worker.ts`, `jobs/autoclose.worker.ts`, `http/routes/media.routes.ts`) — «кому слать» зашито импортом, а не данными |
| Одна группа поддержки | `SUPPORT_GROUP_ID` примерно в 15 местах | Фильтры бота, создание тем, карточка обращения, напоминания |
| База не знает о владельцах | `prisma/schema.prisma` | В `users` нет ссылки на сайт или аккаунт |
| Глобальная уникальность номеров | `schema.prisma:56,64` | `tg_user_id` и `topic_id` уникальны на всю таблицу. Номера тем в разных группах начинаются одинаково — второй клиент упрётся в конфликт. Один и тот же человек может писать двум разным ботам |
| Домены сайтов в переменной окружения | `src/config/env.ts:49`, `src/utils/cors.ts` | Один список на всё приложение; должен принадлежать конкретному сайту и проверяться по базе |
| Виджет знает адрес сервера со сборки | `chat-widget/src/types/config.ts:65` | Не передаёт, чей он. Нужен публичный ключ сайта в строке вставки |
| Имя и аватар оператора берутся у бота | `src/services/bot-info.service.ts:54,95` | Для сервиса даже удобно (владелец настраивает их у @BotFather бесплатно), но переопределение из админки понадобится |
| Сроки напоминаний и тексты — общие | `config/settings.json`, `src/config/messages.ts` | Переезжают в базу, на каждый проект свои |

Что уже есть и переиспользуется без переделки:

- Тексты переписки сохраняются в базе, включая сообщения из Telegram
  (`src/db/repositories/message.repository.ts:47`) — раздел истории самый дешёвый из всего списка.
- Приведение доменов к единому виду, включая кириллические (`src/utils/cors.ts`).
- Ограничение частоты запросов по адресу посетителя (`src/services/rate-limit.service.ts`).
- Проксирование файлов через сервер (`src/http/routes/media.routes.ts`) — но доступ надо закрыть, см. риски.

## Принятые решения

1. **У каждого владельца свой бот.** Он заводит его у @BotFather и вписывает токен
   в админку. Плюсы: свой бренд в Telegram, свои лимиты частоты отправки (клиенты не
   мешают друг другу), аватар и имя настраиваются бесплатно у BotFather.
2. **Один проект = один сайт + один бот + одна группа.** Несколько доменов на проект
   разрешены (основной сайт, зеркала, поддомены) — как сейчас работает список
   разрешённых доменов.
3. **Приём обновлений от Telegram — через webhook, не опросом.** Держать десятки
   постоянных опросов из одного процесса — лишний риск при каждом перезапуске.
   Публичный адрес с сертификатом уже есть; добавляется один входной путь с отдельным
   секретом на бота.
4. **Пока бесплатно.** Тарифы, оплата и счета — не сейчас. Но предел числа проектов
   на аккаунт ставим сразу, иначе первый же робот наделает тысячу пустых.
5. **Масштаб — десятки владельцев.** Инфраструктура не меняется: один контейнер,
   одна база, один Redis. Запас там кратный.
6. **Делаем в текущем репозитории, репозиторий переводим в закрытый** (вариант А из
   разбора ниже). Одна схема базы, одно ядро, одна выкатка. Закрытие ничего не ломает:
   форков и звёзд ноль, выкатка идёт через свой GitHub Actions в свой реестр образов.
   Перевод в закрытый — отдельный шаг перед началом работы, не откладывать «на потом»:
   позже в истории коммитов уже будут проверки доступа к чужой переписке.
7. **Вход в админку через Telegram, а не пароль.** У всех владельцев Telegram есть по
   определению — они там ведут поддержку. Убирает регистрацию, пароли, письма,
   восстановление доступа и почтовый сервис. И сразу даёт то, что иначе делать
   отдельно: мы знаем Telegram-номер владельца и при привязке группы проверяем, что
   код прислал именно он. Экономия 3–4 дня плюс целый класс проблем с безопасностью,
   которых просто не возникает.

## Предложено, ждёт утверждения

1. **Админка на React + Vite отдельной папкой.** Осознанное отступление от аскетизма
   проекта: виджет живёт без внешних зависимостей, потому что встраивается на чужие
   сайты и там важен вес. Админка — наш собственный сайт, вес не важен, а форм и
   таблиц в ней много; на голом TypeScript получится самодельный мини-фреймворк.
   Собирается в статику, раздаётся тем же Fastify, отдельного контейнера не требует.

## Открытые вопросы

- **Экраны админки и путь нового владельца** — не продуманы. Отдельной задачей,
  результат — `docs/saas-platform/admin-design.md`. Оформление уже выбрано (Clearbit,
  разбор ниже), осталось решить состав экранов и переходы между ними.

  Пожелание пользователя: пошаговый мастер подключения, который показывает шаги
  1-2-3 и отмечает уже сделанные. Черновой набор шагов: добавить сайт → завести бота
  у @BotFather и вписать токен → создать группу, добавить бота, отправить код →
  вставить строку с виджетом на сайт → дождаться первого сообщения. Ключевое
  требование к мастеру: шаг отмечается сделанным по настоящей проверке, а не по
  нажатию кнопки — токен проверен обращением к Telegram, группа действительно
  привязана и бот в ней администратор, виджет прислал сигнал с сайта владельца.
- **Юридическая часть.** Обслуживая чужие сайты, вы становитесь обработчиком чужих
  персональных данных: политика конфиденциальности, согласие посетителя в виджете,
  оферта, 152-ФЗ. Для узкого круга знакомых можно отложить, для открытого набора — нет.

## Оформление админки

В `docs/saas-platform/design/` лежат четыре набора стилей, снятых с сайтов через
refero.design: cal.com, Clearbit, ClickUp, monday.com. В каждом — описание
(`DESIGN.md`), готовые переменные оформления (`variables.css`, `theme.css`,
`tokens.json`) и снимок или ролик страницы. Рассматриваем Clearbit и monday.com.

### Общая оговорка

Все четыре набора сняты с **рекламных страниц**, а не с рабочих кабинетов. Видно по
составу: заголовки в 64 пиксела, полоса логотипов «нам доверяют», разрывы между
блоками в 64 пиксела, ширина страницы 1200. Для кабинета набор компонентов другой:
боковое меню, таблицы, формы, состояния «идёт загрузка», «пусто», «ошибка».
Цвета, шрифты и отступы берём как есть, компоненты достраиваем сами.

### Clearbit

Почти бесцветный: тёмно-синие чернила `#091135` на белом, единственный синий
`#127ee3` на кнопках действия, светло-лавандовая подложка `#f5f3ff` для смысловых зон.
Плоский — теней у карточек нет вообще, глубина выражается тонкими рамками `#e1e9f0`.
Скругления: карточки 12, кнопки и поля 8. Шрифт Inter.

- Язык данных: в наборе уже есть таблицы, строки «свойство — значение», значки-метки —
  ровно то, из чего состоят список проектов и история переписки.
- **Inter полностью поддерживает кириллицу.**
- Один акцентный цвет — меньше решений при добавлении экранов, труднее испортить.
- Отсутствие пастели и теней не приедается при ежедневной работе.
- Противоречие в снятом описании: синий `#0f77ff` помечен как «не делать цветом
  действия», а кнопка действия при этом залита `#127ee3`. Решаем так: заливка кнопки —
  `#127ee3`, обводка при наведении и вводе — `#0f77ff`.

### monday.com

Белое поле, пастельные карточки (мятная, небесная, лавандовая), фиолетовый `#6161ff`
как единственный цвет действия. Кнопки-таблетки со скруглением 160, карточки 24.
Шрифт Poppins.

- Дружелюбнее и мягче, лучше подходит рекламной странице сервиса.
- **Poppins не поддерживает кириллицу.** Русские заголовки браузер подставит запасным
  шрифтом, и всё оформление поедет. Из предложенных в наборе замен кириллицу держит
  **Manrope** — если берём monday.com, шрифт только он.
- Пастельные карточки хороши для плиток, но у одного владельца проектов единицы;
  в таблице истории обращений разноцветье мешает читать.
- Кнопки шириной в таблетку и скругления 24 съедают место — в плотных таблицах хуже.

### Решение

**Взят Clearbit** (решено 2026-08-04). Причины: кириллица в Inter без замен и
оговорок; готовый язык таблиц и строк данных; один акцентный цвет; спокойный вид,
который не надоедает при ежедневной работе.

monday.com пригодится, если у сервиса будет рекламная страница — там его
дружелюбность уместнее. Тогда возможен размен: страница в духе monday.com, кабинет в
духе Clearbit. Это два набора стилей вместо одного; браться за него стоит, только
когда рекламная страница действительно понадобится.

## План работ

Разбивка такая, что каждая часть выкатывается отдельно и не ломает работающее.

1. **Модель данных и перенос текущего клиента.** Аккаунт, проект, домены; всё нынешнее
   становится проектом №1. Уникальность номера темы и Telegram-посетителя — в пределах
   проекта. Поведение работающих сайтов не меняется ни на шаг.
2. **Много ботов.** Webhook, реестр ботов, замена глобального бота на «бота проекта» во
   всех сервисах, задачах и очередях. Самая объёмная и рискованная часть.
3. **Вход в админку и каркас.** Вход через Telegram, аккаунт, список проектов.
4. **Подключение проекта.** Добавление токена с проверкой через Telegram, привязка
   группы кодом со всеми проверками, готовая строка вставки для сайта.
5. **Настройки виджета.** Имя и аватар оператора, цвет, положение, приветствие; виджет
   забирает их с сервера по ключу сайта. Заодно закрывается задача про вшитый адрес
   (`Telegram-support-bot-f6a`).
6. **История обращений.** Данные уже в базе, нужна страница со списком, поиском и перепиской.

Части 5 и 6 при желании откладываются на «после запуска» — первые владельцы проживут
на настройках бота у BotFather.

### Проверки при привязке группы

Это не «отправил код и готово». Перед привязкой проверяем и объясняем понятным
языком, что не так:

- группа именно супергруппа, а не обычная;
- в ней включены темы (форум);
- бот добавлен и он администратор с правом управлять темами;
- код прислал владелец аккаунта, а не случайный участник;
- эта группа ещё не привязана к другому аккаунту.

Если здесь сэкономить на сообщениях об ошибках — половина владельцев застрянет.

## Оценка

| Часть | Объём |
|---|---|
| Модель данных и перенос текущего клиента | 3–5 дней |
| Много ботов | 4–6 дней |
| Вход и каркас админки | 2–3 дня |
| Подключение проекта | 3–4 дня |
| Настройки виджета | 2–3 дня |
| История обращений | 2–3 дня |
| Изоляция и безопасность, проверка на утечки между владельцами | 3–4 дня |

**Итого 3–4,5 недели** полной работы до состояния «можно отдавать посторонним».
Урезанная рабочая версия (части 1–4) — около двух недель.

Самое дорогое здесь не админка, её делать приятно. Дорогая вторая часть: протащить
«какой это проект» через три десятка мест, включая задачи, которые в момент выкатки
уже лежат в очереди Redis со старым набором полей.

## Риски

- **Утечка между владельцами — главный.** Каждый запрос к базе обязан фильтроваться
  по владельцу. Одна забытая проверка = чужая переписка на экране. Нужны отдельные
  тесты именно на это.
- **Проксирование файлов.** Сейчас файл по `/api/media/:fileId` скачает любой, кто
  знает идентификатор. При нескольких владельцах это утечка между ними; доступ надо
  привязать к проекту и сессии.
- **Работающая боевая поддержка.** На сервисе живут три сайта. Перестройку делаем в
  ветке, первым шагом — перенос «всё нынешнее = проект №1», наполовину не выкатываем.
- **Задачи в очереди на момент выкатки.** В Redis лежат отложенные напоминания и
  автозакрытия со старым набором полей. Нужен план: либо доработать обработчики так,
  чтобы старые задачи не падали, либо очистить очередь в момент выкатки.
- **Отозванный токен или удалённая группа.** Владелец может удалить бота или группу в
  любой момент. Приложение должно это пережить и показать понятное сообщение в админке.

## Где делать: решено — текущий репозиторий, перевести в закрытый

**Решение принято 2026-08-04: вариант А.** Ниже разбор, на котором оно основано.

Отдельный довод в пользу закрытия: репозиторий сейчас открыт, форков и звёзд ноль.
Пока это бот для одного бизнеса, открытый код безвреден — секретов в нём нет, все
ключи в переменных окружения. Как только хранится переписка чужих клиентов, открытый
код показывает любому желающему, как устроены проверки доступа, и позволяет искать в
них дыры без учётной записи. Для больших проектов с аудитом это нормальная практика,
для сервиса, который делают вдвоём, — бесплатная подсказка нападающему.

Рассмотрены три варианта.

**А. Всё в текущем репозитории**, админка — отдельная папка со своей сборкой, по
образцу `chat-widget/`; её серверная часть в существующем Fastify.

- Схема базы одна, миграции в одном месте.
- Ядро (бот, веб-чат, работа с темами) переиспользуется целиком.
- Выкатка одна: один образ в Coolify, один домен.
- Минус: репозиторий растёт, в нём соседствуют три пакета.

**Б. Админка в отдельном репозитории**, общая база с основным приложением.

- Минус тяжёлый: два репозитория ходят в одну базу, а описание схемы лежит в одном из
  них. Любое изменение схемы — согласование вручную, расхождения неизбежны.
- Второй контейнер, второй домен, вторая выкатка.
- Плюс появляется, только если админку пишет другая команда или на другом стеке.

**В. Новый репозиторий под сервис**, текущий заморозить как версию для нынешнего клиента.

- Плюс: работающая поддержка не под угрозой, можно проектировать с чистого листа.
- Минус: два кода, которые расходятся с первого дня. Исправление в одном надо
  переносить в другой руками. Нынешнего клиента всё равно придётся переводить на
  сервис — иначе поддерживать вечно два.

**Выбран вариант А.** Причины — одна схема базы, одно ядро, одна выкатка, и уже есть
образец разделения на пакеты внутри репозитория (`chat-widget/` со своими правилами и
сборкой). Вариант В выглядит безопасным, но безопасность там мнимая: расхождение двух
копий обойдётся дороже, чем аккуратная ветка.

Единственная причина держать репозиторий открытым — использовать его как витрину
своей работы. Это осознанный размен, и признать его надо вслух, а не оставить по
умолчанию.
